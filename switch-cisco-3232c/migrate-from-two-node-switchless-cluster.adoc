= Migration von einem Zwei-Knoten Cluster ohne Switches zu einem Cluster mit Cisco Nexus 3232C Cluster Switches
:allow-uri-read: 
:icons: font
:imagesdir: ../media/


[role="lead"]
Wenn Sie ein Cluster ohne Switches mit zwei Knoten haben, kann auf ein Cluster mit Switches mit zwei Knoten migriert werden, das Cisco Nexus 3232C Cluster Network Switches umfasst. Dies ist ein unterbrechungsfreies Verfahren.



[[review-requirements]]
== Überprüfungsanforderungen

.Bevor Sie beginnen
Überprüfen Sie die folgenden Installationen und Verbindungen:

* Für Knotenverbindungen stehen Ports zur Verfügung. Die Cluster Switches nutzen die Inter-Switch Link (ISL) Ports e1/31-32.
* Sie verfügen über die passenden Kabel für die Clusterverbindungen:
+
** Die Knoten mit 10 GbE Clusterverbindungen benötigen QSFP-Lichtwellenleitermodule mit Breakout-Glasfaserkabeln oder QSFP zu SFP+ Kupfer-Breakout-Kabeln.
** Die Knoten mit 40/100 GbE Cluster-Verbindungen benötigen unterstützte QSFP/QSFP28 optische Module mit Glasfaserkabeln oder QSFP/QSFP28 Kupfer-Direktanschlusskabel.
** Die Cluster-Switches erfordern die entsprechende ISL-Verkabelung: 2x QSFP28 Glasfaser- oder Kupfer-Direktanschlusskabel.


* Die Konfigurationen sind ordnungsgemäß eingerichtet und funktionieren.
+
Die beiden Knoten müssen verbunden und funktionsfähig in einer Zwei-Knoten Cluster ohne Switches Umgebung sein.

* Alle Cluster-Ports befinden sich im Status *up*.
* Die Cisco Nexus 3232C Cluster Switches werden unterstützt.
* Die bestehende Cluster-Netzwerkkonfiguration weist folgende Merkmale auf:
+
** Eine redundante und voll funktionsfähige Nexus 3232C Cluster Infrastruktur auf beiden Switches
** Die neuesten RCF und NX-OS Versionen auf Ihren Switches
** Management-Konnektivität auf beiden Switches
** Konsolenzugriff auf beide Switches
** Alle logischen Schnittstellen (LIFs) des Clusters im Status *up* ohne Migration
** Erste Anpassung des Switches
** Alle ISL Ports sind aktiviert und verkabelt.




.Zu den Beispielen
Die Beispiele in diesem Verfahren verwenden die folgende Schalter- und Knotennomenklatur:

* Nexus 3232C Cluster Switches, C1 und C2.
* Die Knoten sind n1 und n2.


Die Beispiele in diesem Verfahren verwenden zwei Knoten, die jeweils zwei 40-GbE-Cluster-Verbindungsports e4a und e4e nutzen. Die link:https://hwu.netapp.com/["Hardware Universe"^] enthält Details zu den Cluster-Ports Ihrer Plattformen.

* n1_clus1 ist die erste logische Schnittstelle (LIF), die mit dem Cluster-Switch C1 für Knoten n1 verbunden wird.
* n1_clus2 ist die erste Cluster-LIF, die mit dem Cluster-Switch C2 für Node n1 verbunden wird.
* n2_clus1 ist die erste Cluster-LIF, die mit dem Cluster-Switch C1 für Node n2 verbunden wird.
* n2_clus2 ist die zweite Cluster-LIF, die mit dem Cluster-Switch C2 für Node n2 verbunden wird.
* Die Anzahl der 10 GbE- und 40/100 GbE-Ports ist in den Referenzkonfigurationsdateien (RCFs) definiert, die unter link:https://mysupport.netapp.com/site/products/all/details/cisco-cluster-storage-switch/downloads-tab["Cisco Cluster Netzwerk Switch Referenzkonfigurationsdatei herunterladen"^] verfügbar sind.


[NOTE]
====
Für dieses Verfahren werden sowohl ONTAP Befehle als auch Cisco Nexus 3000 Series Switches Befehle benötigt; ONTAP Befehle werden verwendet, sofern nicht anders angegeben.

`network interface migrate cluster -lif _lif-name_ -source-node _source-node-name_ -destination-node _destination-node-name_ -destination-port _destination-port-name_`

+
.Beispiel anzeigen
[%collapsible]
====
Jede LIF muss einzeln an ihren jeweiligen Heimatport migriert werden, wie im folgenden Beispiel gezeigt:

[listing, subs="+quotes"]
----
cluster::*> *network interface migrate -vserver cluster -lif n1_clus2 -source-node n1
-destination-node n1 -destination-port e4a*
cluster::*> *network interface migrate -vserver cluster -lif n2_clus2 -source-node n2
-destination-node n2 -destination-port e4a*
----
====
. Cluster-Ports clus2 LIF auf beiden Knoten herunterfahren:
+
`network port modify`

+
.Beispiel anzeigen
[%collapsible]
====
Das folgende Beispiel zeigt die angegebenen Ports, die auf  `false` gesetzt werden, wodurch die Ports auf beiden Knoten deaktiviert werden:

[listing, subs="+quotes"]
----
cluster::*> *network port modify -node n1 -port e4e -up-admin false*
cluster::*> *network port modify -node n2 -port e4e -up-admin false*
----
====

. Das Kabel von e4e am Node n1 abziehen.
+
Es kann auf die laufende Konfiguration Bezug genommen und der erste 40-GbE-Port am Switch C2 (Port 1/7 in diesem Beispiel) mit e4e am Node n1 über die geeignete Verkabelung für das Switch-Modell Nexus 3232C verbunden werden.

. Das Kabel von e4e an Node n2 abziehen.
+
Die laufende Konfiguration kann herangezogen und e4e mit dem nächsten verfügbaren 40 GbE Port auf C2, Port 1/8, unter Verwendung der für das Nexus 3232C Switch-Modell geeigneten Verkabelung verbunden werden.

. Alle zum Knoten führenden Ports auf C2 aktivieren.
+
.Beispiel anzeigen
[%collapsible]
====
Das folgende Beispiel zeigt Ports 1 bis 30, die auf den Nexus 3132Q-V Cluster Switches C1 und C2 mit einer in RCF unterstützten Konfiguration aktiviert werden  `NX3232C_RCF_v1.0_24p10g_26p100g.txt`:

[listing, subs="+quotes"]
----
C2# *configure*
C2(config)# *int e1/1/1-4,e1/2/1-4,e1/3/1-4,e1/4/1-4,e1/5/1-4,e1/6/1-4,e1/7-30*
C2(config-if-range)# *no shutdown*
C2(config-if-range)# *exit*
C2(config)# *exit*
----
====
. Den zweiten Cluster-Port, e4e, auf jedem Knoten aktivieren:
+
`network port modify`

+
.Beispiel anzeigen
[%collapsible]
====
Das folgende Beispiel zeigt, dass der zweite Cluster-Port e4e auf jedem Knoten aktiviert wird:

[listing, subs="+quotes"]
----
cluster::*> *network port modify -node n1 -port e4e -up-admin true*
cluster::*> *network port modify -node n2 -port e4e -up-admin true*s
----
====
. Für jeden Knoten sind alle migrierten Cluster Interconnect-LIFs wiederherzustellen: `network interface revert`
+
.Beispiel anzeigen
[%collapsible]
====
Das folgende Beispiel zeigt, dass die migrierten LIFs auf ihre ursprünglichen Ports zurückgesetzt werden.

[listing, subs="+quotes"]
----
cluster::*> *network interface revert -vserver Cluster -lif n1_clus2*
cluster::*> *network interface revert -vserver Cluster -lif n2_clus2*
----
====
. Es sollte überprüft werden, ob alle Cluster-Interconnect-Ports nun wieder auf ihre Home-Ports zurückgesetzt sind:
+
`network interface show -role cluster`

+
Die Spalte `Is Home` sollte für alle in der Spalte `Current Port` aufgelisteten Ports einen Wert von `true` anzeigen. Wenn der angezeigte Wert `false` ist, wurde der Port nicht zurückgesetzt.
